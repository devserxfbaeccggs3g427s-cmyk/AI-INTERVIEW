Minh họa thuật toán Redlock Quorum & Fencing Token Pattern

Quorum 3/5 Node Độc Lập
Quorum 3/5 Nodes + Monotonic Fencing Token Validity Time = TTL - (T_acquire + Drift)
Nguy cơ NTP Jump: Đồng hồ lệch làm TTL hết hạn sớm tại node Quorum Đạt: 3 node >= (5/2 + 1)
So sánh đánh đổi kiến trúc thực chiến (CP vs AP)
Tiêu chí Redis Redlock etcd / ZooKeeper Postgres Advisory Lock
Mô hình nhất quán AP (Heuristic, phụ thuộc clock) Strict CP (Raft / ZAB) ACID Database Session
Throughput & Latency >100k ops/sec (<1ms) 10k - 20k ops/sec (~5ms) 1k - 5k ops/sec (~15ms)

Cấu trúc phản xạ 90s giúp ghi trọn điểm Senior / Staff
90 Giây Bar
1. BÀI TOÁN & PRIMITIVE CƠ BẢN 00 - 20s

“Để làm distributed lock, lệnh nguyên tử chuẩn là SET key val NX PX 30000 kèm random value để release an toàn bằng Lua script. Tuy nhiên single-node Redis không an toàn do replica sync bất đồng bộ — master chết là mất lock.”

2. NGUYÊN LÝ REDLOCK & QUORUM 20 - 45s

“Giải pháp Redlock dùng N master độc lập (thường N=5). Client gửi lệnh lock đồng thời, nếu acquire thành công quá bán (≥3 node) trong thời gian nhỏ hơn TTL, lock hợp lệ với validity = TTL - T_acquire.”

3. PHẢN BIỆN GC PAUSE & FENCING TOKEN 45 - 70s

“Nhưng Martin Kleppmann chỉ ra: nếu client bị GC pause 15 giây, lock đã hết hạn trên Redis mà client không biết. Vì vậy tại storage layer phải dùng Fencing Token tăng dần — DB sẽ reject mọi write request mang token cũ.”

4. KẾT LUẬN ĐÁNH ĐỔI (TRADE-OFF) 70 - 90s

“Tóm lại: Nếu cần throughput hàng chục ngàn ops/giây và chấp nhận rủi ro cực nhỏ, Redlock là tốt nhất. Còn nếu tiền bạc tài chính yêu cầu strict correctness, em sẽ chọn etcd hoặc ZooKeeper dùng mô hình Raft CP.”
